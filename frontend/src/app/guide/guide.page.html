01 / ENTENDER

Dos backends, dos responsabilidades

hub

El backend de Órbita / ClassForge

Es el servidor que permite usar esta plataforma: autentica usuarios, guarda proyectos, valida el modelo UML y sincroniza las acciones de colaboradores.

También importa y exporta XMI, consulta los proveedores de IA y genera archivos descargables. El nombre técnico del proyecto sigue siendo ClassForge.

Java 21 · Spring Boot · JPA · WebSocket
deployed_code

El backend que descargas

Es un proyecto independiente creado a partir de tus clases y relaciones. Incluye entidades, repositorios, servicios y endpoints CRUD para los datos de tu aplicación.

El modo con autenticación añade login y JWT. El ZIP incluye documentación OpenAPI, colección Postman y clientes Angular y Flutter. Necesita ejecutarse por separado.

Tu modelo → proyecto Spring Boot → API REST

Funciones disponibles en la plataforma

  • Cuenta y acceso Registro, login y proyectos propios o compartidos.
  • Modelado Clases, atributos, métodos, relaciones, multiplicidades y clases de asociación. Los métodos documentan operaciones con parámetros y retorno; no generan lógica de negocio.
  • Trabajo en equipo Invitaciones por correo, presencia, sincronización de operaciones, chat compartido e historial de actividad.
  • Control del modelo Guardado, revisiones, deshacer/rehacer y validación con observaciones.
  • Intercambio Vista previa de importación y exportación XMI para Enterprise Architect.
  • Generación ZIP con API CRUD simple o autenticada y aplicaciones cliente.
  • Asistencia Texto, voz e imagen con revisión previa de los cambios. Requiere servicios de IA configurados.
La conversación del equipo y la actividad se guardan en la base de datos del servidor y se actualizan cada 4 segundos. Solo los miembros del proyecto pueden consultarlas. La actividad empieza a registrarse desde esta versión. El modo Consultar usa el modelo guardado y permite incluir hasta 20 mensajes recientes del equipo, con un máximo de 600 caracteres por mensaje. Tus preguntas y respuestas exitosas se guardan de forma privada por usuario y proyecto; puedes recuperar y borrar el historial. La IA recibe hasta 10 intercambios anteriores, con respuestas limitadas a 2000 caracteres. Las propuestas de cambio no forman parte de esa memoria. La pestaña Resumen calcula operaciones por período e integrante, sin IA, con hasta 90 días por consulta. Los resúmenes se actualizan al solicitarlos.

Estas instrucciones son para PowerShell en Windows. Abre las terminales desde la raíz del repositorio ClassForge.

03 / TU APLICACIÓN GENERADA

Descargar, iniciar y demostrar el backend

  1. Entra a un proyecto y crea o importa tu diagrama. Marca los identificadores de las clases y valida el modelo.
  2. Espera la sincronización y pulsa Descargar backend. Elige nombre, paquete Java y modo CRUD simple o autenticado.
  3. Extrae el ZIP. Abre PowerShell en la carpeta que contiene build.gradle y gradlew.bat.
  4. Ejecuta el comando y espera el mensaje Started …Application.

Arrancar el proyecto exportado

La API utiliza http://localhost:8080 por defecto. bootRun permanece ejecutándose mientras el servidor está encendido; el porcentaje de Gradle no tiene que llegar a 100 %. Detén el servidor con Ctrl+C.

Probar los endpoints reales

  1. Importa postman_collection.json en Postman y revisa la URL base de la colección para que apunte a tu servidor local.
  2. Utiliza los nombres de rutas y cuerpos que aparecen en la colección o en openapi.yaml. Se derivan del modelo; no supongas que el nombre de la clase se pluraliza automáticamente.
  3. Ejecuta crear → listar → obtener → actualizar → contar → eliminar. Comprueba la respuesta de cada operación.
  4. Si elegiste autenticación, crea la primera cuenta con POST /api/auth/bootstrap, usando el cuerpo indicado en la colección. Después inicia sesión con POST /api/auth/login y envía el JWT como Bearer Token.

Las claves compuestas utilizan /by-id con parámetros. Las relaciones se envían mediante identificadores; crea primero los registros referenciados.

Datos de demostración: el ZIP usa H2 en memoria y ddl-auto: create-drop. Esos registros desaparecen al reiniciar. Las nuevas exportaciones usan update en el perfil PostgreSQL para conservar datos; los ZIP anteriores deben revisarse. Antes de producción prepara migraciones y copias de seguridad.
Usar PostgreSQL local con persistencia

Crea antes la base y el usuario. Sustituye los valores de ejemplo. update permite una demostración persistente; para producción con cambios de esquema controlados, prepara migraciones y usa una política acorde.

Ejecutar los clientes incluidos en el ZIP

En frontend/ ejecuta npm install y npm start. Su proxy espera esta API en el puerto 8080. Para Android, instala Flutter y Android SDK; en mobile/ ejecuta flutter pub get y flutter run. El emulador Android accede al equipo mediante 10.0.2.2:8080; un teléfono físico necesita una URL de API accesible.

Estas aplicaciones administran los datos del sistema que generaste. No son el editor colaborativo de Órbita.

05 / SERVICIOS OPCIONALES

Activar los asistentes

En el editor abre Texto y voz o Imagen a UML. Los paneles consultan la disponibilidad del proveedor; que la API esté encendida no significa que los modelos estén ejecutándose.

En Texto y voz puedes elegir entre los proveedores habilitados en el servidor y pulsar Comprobar conexión. La preferencia se conserva en este navegador por proyecto y se envía en cada consulta o propuesta. Para voz se usa Whisper antes del proveedor de texto seleccionado; imágenes conserva su configuración propia. El estado Configurado de Bedrock no garantiza credenciales ni acceso al modelo: eso se comprueba al solicitar una respuesta. Las claves y URLs se configuran únicamente en el backend.

  • Texto: servidor llama.cpp con modelo compatible y herramientas, por defecto en 8092.
  • Voz: whisper-server con modelo multilingüe, por defecto en 8093, además del proveedor de texto.
  • Imagen: servidor multimodal compatible, por defecto en 8094.
  • Alternativa externa: existe integración con Amazon Bedrock. Requiere habilitarla, configurar región/modelos y credenciales en el servidor, y tener acceso a esos modelos.

Estas son variables del backend de la plataforma. El ZIP generado utiliza otras: LLAMA_URL, LLAMA_MODEL, WHISPER_URL y APP_API_BASE_URL, descritas en su README.

En Railway, 127.0.0.1 identifica el contenedor, no tu computadora. Configura servicios accesibles desde el backend. Las claves de proveedores se guardan en el servidor; no en el frontend. El micrófono necesita permisos y HTTPS o localhost.
06 / RESOLVER PROBLEMAS

Antes de volver a intentarlo

Gradle se queda en EXECUTING / bootRun

Busca Started …Application y el puerto de Tomcat en los logs. Si ya aparecen, el servidor está atendiendo. IDLE describe workers de Gradle, no un error. La primera ejecución puede descargar dependencias; los errores reales aparecen en los logs.

Java o Node no tienen la versión correcta

Comprueba java -version, javac -version y node --version. Después de instalar, abre una terminal nueva. En Windows, where.exe java muestra qué instalación tiene prioridad. JAVA_HOME debe apuntar a la carpeta del JDK, no a bin.

El puerto 8080 está ocupado

Para el backend generado puedes elegir otro puerto:

Actualiza también Postman, el proxy de los clientes y APP_API_BASE_URL si usas el asistente generado.

La API devuelve 401 o no puedo generar

Inicia sesión de nuevo y verifica el Bearer Token. Antes de exportar espera las operaciones pendientes, guarda los cambios locales y valida el modelo. El diálogo de generación muestra problemas de identificadores, tipos o relaciones.

Los datos desaparecen al reiniciar

Revisa si utilizas H2 en memoria, create-drop o almacenamiento efímero del contenedor. Para conservar información, configura una base persistente y evita create-drop. En la plataforma, H2 en archivo también necesita un volumen persistente si se usa dentro de un contenedor.
